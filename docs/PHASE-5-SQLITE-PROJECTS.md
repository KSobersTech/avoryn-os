# Phase 5 Specification: SQLite Projects Foundation

**Status:** Approved for implementation  
**Target branch:** `feature/sqlite-foundation`  
**Milestone:** First complete persistent vertical slice

## Objective

Phase 5 will prove AVORYN's full desktop architecture by implementing a Projects workflow that persists data locally through the Rust backend.

```text
React form
→ typed frontend service
→ Tauri command
→ Rust validation
→ application service
→ SQLx repository
→ SQLite
→ audit event
→ typed response
→ rendered project list
```

The milestone is complete only when a project remains available after AVORYN is closed and reopened.

## Scope

### Included

- SQLx configured for SQLite
- versioned database migrations
- application-data database location
- `projects` table
- `audit_events` table
- Rust project domain types
- project validation
- create, list, get, and update project commands
- typed frontend project contracts
- Projects page creation form
- Projects page list and empty state
- structured user-safe errors
- persistence verification after restart
- automated backend tests for critical behavior

### Excluded

- project deletion and archival approval flow
- tasks linked to projects
- clients and invoices
- file attachments
- tags and milestones
- time tracking
- portfolio export
- cloud synchronization
- AI-generated project content

These features will be introduced after the first persistent slice is stable.

## Project Data Model

### `projects`

| Column | Type | Rules |
|---|---|---|
| `id` | TEXT | UUID primary key generated by Rust |
| `name` | TEXT | required, trimmed, 1–120 characters |
| `description` | TEXT | optional, maximum 2,000 characters |
| `workspace` | TEXT | required approved enum value |
| `project_kind` | TEXT | required approved enum value |
| `status` | TEXT | required, defaults to `planned` |
| `priority` | TEXT | required approved enum value |
| `start_date` | TEXT | optional ISO-8601 calendar date |
| `due_date` | TEXT | optional ISO-8601 calendar date |
| `completed_at` | TEXT | optional UTC timestamp |
| `created_at` | TEXT | required UTC timestamp |
| `updated_at` | TEXT | required UTC timestamp |
| `deleted_at` | TEXT | optional UTC soft-delete timestamp |

## Audit Model

The first audit implementation will record significant persistent actions without storing sensitive content.

### `audit_events`

| Column | Type | Rules |
|---|---|---|
| `id` | TEXT | UUID primary key |
| `request_id` | TEXT | request correlation identifier |
| `event_type` | TEXT | stable event name |
| `resource_type` | TEXT | `project` for Phase 5 |
| `resource_id` | TEXT | affected project UUID |
| `outcome` | TEXT | `success` or `failure` |
| `created_at` | TEXT | UTC timestamp |

Phase 5 event names:

- `project.created`
- `project.updated`

The audit log must not store complete descriptions or other unnecessary personal content.

## Frontend Creation Form

The first Projects form will request:

- project name
- description
- workspace
- project kind
- priority
- optional due date

Rust will automatically generate:

- UUID
- initial status of `planned`
- creation timestamp
- update timestamp

## React-to-Rust Commands

### `create_project`

Creates and returns one persisted project.

### `list_projects`

Returns non-deleted projects with pagination support.

### `get_project`

Returns one project by UUID or a stable not-found error.

### `update_project`

Updates allowed fields and uses `expected_updated_at` for optimistic concurrency control.

## Validation Rules

- Project names are trimmed and cannot be blank.
- Project names cannot exceed 120 characters.
- Descriptions cannot exceed 2,000 characters.
- Workspace, project kind, status, and priority must match approved values.
- UUID inputs must be valid UUIDs.
- Date values must use supported ISO-8601 formatting.
- A due date cannot be earlier than a provided start date.
- Backend validation remains authoritative even when React validates first.
- SQL must be parameterized.

## Stable Error Codes

- `PROJECT_NAME_REQUIRED`
- `PROJECT_NAME_TOO_LONG`
- `PROJECT_DESCRIPTION_TOO_LONG`
- `PROJECT_WORKSPACE_INVALID`
- `PROJECT_KIND_INVALID`
- `PROJECT_STATUS_INVALID`
- `PROJECT_PRIORITY_INVALID`
- `PROJECT_DATE_INVALID`
- `PROJECT_DATE_RANGE_INVALID`
- `PROJECT_NOT_FOUND`
- `PROJECT_VERSION_CONFLICT`
- `DATABASE_UNAVAILABLE`
- `DATABASE_OPERATION_FAILED`
- `UNEXPECTED_ERROR`

User-facing messages must remain understandable and must not expose raw SQL, internal paths, or stack traces.

## Projects Page States

The interface must support:

- initial loading state
- empty state
- create-project form
- submitting state
- validation feedback
- successful project list
- recoverable backend error state
- retry behavior for list failures

## Acceptance Criteria

1. AVORYN starts and initializes the database automatically.
2. Migrations run successfully on a new database.
3. The Projects page shows a clear empty state when no projects exist.
4. A valid project can be created from the React interface.
5. Rust validates the request before persistence.
6. SQLite stores the project through parameterized SQL.
7. The saved project is returned as a typed response.
8. The project appears in the Projects list without restarting.
9. An audit event is created for successful project creation.
10. Closing and reopening AVORYN preserves the project.
11. Blank and oversized names are rejected.
12. Invalid enum and date values are rejected by Rust.
13. Internal errors are converted to stable, user-safe errors.
14. Backend tests cover creation, retrieval, validation, migration, and persistence behavior.
15. Required quality checks pass before the feature is merged.
